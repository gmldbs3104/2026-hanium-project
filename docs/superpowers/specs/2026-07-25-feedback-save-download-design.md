# 피드백 화면 저장·다운로드 UX 정리 설계

> 작성일: 2026-07-25
> 대상: `frontend/lib/features/feedback/screens/feedback_screen.dart`
> 관련: `frontend_작업현황4.md` 5절 "다운로드 버튼 수정 요망" — UX 정리 항목
> 관련 요구사항: SFR-007, SFR-009 (REQ-009-4, REQ-009-5)

## 1. 문제

피드백 화면에 "저장"으로 읽히는 요소가 세 개 있어 사용자가 무엇이 어디에 저장되는지 구분할 수 없다.

| 위치 | 현재 라벨 | 실제 동작 | 근거 |
| --- | --- | --- | --- |
| AppBar 아이콘 | (툴팁) 이미지 다운로드 | 화면 캡처 PNG를 **사용자 기기로** 내려받기 | requirement에 없음 — 부가 기능 (`160e493`) |
| 하단 주 버튼 | 확인 (결과 저장) | 분석 결과를 **서버 DB에** 영구 저장 | SFR-009 / REQ-009-1~3 (필수) |
| 체크박스 (이미지 모드) | 원본 이미지도 함께 저장하기 | 촬영 원본을 **서버 S3에** 업로드 동의 | REQ-009-4 (필수) |

세 요소는 기능이 겹치지 않는다. 목적지가 "내 기기"와 "서버"로 다를 뿐이며, 하단 버튼은 SFR-007 Post-condition을 만족시키는 필수 트리거라 제거할 수 없다. **따라서 이 작업은 기능 통합이 아니라 문구·배치 정리다.**

## 2. 결정: 한 단어에 한 뜻

> **"저장" = 서버로. "받기" = 내 기기로.**

이 원칙에 따라 화면 전체 문구를 통일한다.

| 위치 | 변경 전 | 변경 후 |
| --- | --- | --- |
| AppBar 아이콘 | `⬇` (툴팁 "이미지 다운로드") | **제거** (하단으로 이동, AppBar엔 오버레이 토글만) |
| 하단 주 버튼 | `확인 (결과 저장)` | `학습 기록 저장` |
| 하단 보조 버튼 | (없음) | `⬇ 이미지 받기` |
| 체크박스 | `원본 이미지도 함께 저장하기` | `촬영한 원본 사진도 서버에 보관` |
| 체크박스 설명 | 동의하지 않으면 분석 결과만 저장되고, 촬영한 사진은 저장되지 않습니다. | 체크하지 않으면 분석 결과만 저장되고, 사진은 서버에 남지 않아요. |
| 저장 완료 문구 | `저장이 완료되었습니다.` | `학습 기록을 저장했어요.` |
| 저장 성공 스낵바 | `학습 결과가 저장되었습니다.` | `학습 기록을 저장했어요.` |
| 다운로드 성공 스낵바 | `이미지를 다운로드했어요.` | `이미지를 기기에 받았어요.` |

부수 정리: `frontend/lib/core/app_config.dart:37`의 주석 `피드백 화면에서 "확인" 탭 시 트리거`가 라벨 변경 후 낡은 표현이 되므로 함께 갱신한다.

### 판단 근거

**"확인"을 라벨에서 뺀 이유.** requirement SFR-007 Post-condition은 "사용자가 피드백을 확인(confirm)하면 SFR-009가 트리거된다"이다. '확인'은 트리거 조건을 설명하는 말이고 사용자가 실제로 하는 일은 저장이다. 둘을 한 라벨에 넣으니 `확인 (결과 저장)`처럼 괄호가 붙었다. 트리거 관계는 코드 주석에 이미 기록되어 있으므로 라벨은 행동만 말한다.

**체크박스에 "서버에"를 명시한 이유.** 이 체크박스는 저장 버튼의 하위 옵션이라 같은 '저장' 계열 표현이 맞지만, 그것만으로는 기기 저장과 구분되지 않는다. 목적지를 문구에 넣으면 바로 옆 "이미지 받기"와 대비되어 구분된다.

## 3. 배치

다운로드를 AppBar에서 하단으로 옮겨 두 행위를 같은 줄에 놓는다. 목적지 차이를 나란히 비교할 수 있게 하되, 주된 행동(저장)이 폭으로 위계를 갖는다.

```
[저장 전]                             [저장 후]
┌───────────────────────────────┐   ┌───────────────────────────────┐
│ ☐ 촬영한 원본 사진도 서버에 보관 │   │  ✓ 학습 기록을 저장했어요       │
│   체크하지 않으면 분석 결과만…   │   │                               │
│                               │   │  [⬇ 이미지 받기]  [홈으로]      │
│ [⬇ 이미지 받기][ 학습 기록 저장 ]│   └───────────────────────────────┘
│   flex:1        flex:2         │
└───────────────────────────────┘
```

저장 완료 후에도 "이미지 받기"를 남긴다. 저장을 끝낸 뒤 결과물을 챙기는 흐름이 자연스러운데, 현재는 그 시점에 하단이 "저장 완료 + 홈으로"로 바뀌면서 다운로드 수단이 사라진다.

저장 완료 상태(`confirmed: true`)에서는 원본 사진 보관 체크박스를 노출하지 않는다(현재 동작과 동일). 이미 저장 요청이 끝난 뒤라 동의를 바꿔도 반영할 경로가 없기 때문이다. 완료 영역의 `이미지 받기`는 외곽선 버튼, `홈으로`는 텍스트 버튼으로 둔다.

## 4. 구조

`_buildConfirmSection`(약 55줄)을 새 위젯으로 분리한다. `feedback_screen.dart`는 이미 640줄이고, 이번에 손댈 영역이 정확히 여기라 함께 떼어낸다. 분리하면 API mock·라우터 없이 하단 바만 위젯 테스트할 수 있다.

**신규**: `frontend/lib/features/feedback/widgets/feedback_action_bar.dart`

```dart
/// 피드백 화면 하단 액션 영역 (SFR-009 저장 + 기기 다운로드)
///
/// "저장" = 서버로, "받기" = 기기로 — 두 목적지를 라벨에서 구분한다.
class FeedbackActionBar extends StatelessWidget {
  final bool isCanvas;           // false일 때만 원본 사진 보관 동의 노출 (REQ-009-4)
  final bool confirmed;          // 저장 완료 후 레이아웃으로 전환
  final bool isConfirming;
  final bool isDownloading;
  final bool saveImageConsent;
  final ValueChanged<bool> onConsentChanged;
  final VoidCallback onConfirm;
  final VoidCallback onDownload;
  final VoidCallback onGoHome;
}
```

상태를 갖지 않는 `StatelessWidget`이다. 파라미터가 9개로 넓지만 전부 표시에 필요한 값이며, API 호출과 상태 변경은 전부 화면 쪽에 남는다. 이 위젯은 받은 값을 그리고 탭을 콜백으로 넘기는 일만 한다.

**변경**: `frontend/lib/features/feedback/screens/feedback_screen.dart`

- AppBar `actions`에서 다운로드 `IconButton` 제거 → 오버레이 토글만 남김
- `_buildConfirmSection` 삭제 → `FeedbackActionBar(...)` 호출로 교체
- `_downloadFeedbackImage`, `_onConfirm`, `_overlayCaptureKey`는 화면에 유지

순증감 추정: 화면 −60줄, 신규 위젯 +110줄.

**좁은 화면 대비.** 두 버튼이 한 줄에 들어가므로 라벨에 `maxLines: 1, overflow: TextOverflow.ellipsis`를 건다. 없으면 좁은 기기에서 RenderFlex 오버플로가 난다.

**진행 중 표시.** 각 버튼은 자기 작업 중일 때만 스피너로 바뀌고 비활성화된다. 저장과 다운로드는 독립이므로 한쪽이 진행 중이어도 다른 쪽은 누를 수 있다.

## 5. 동작·에러 처리

**동작 로직은 변경하지 않는다.** `_onConfirm`의 오프라인 큐 분기(`79a940e`에서 수정한 4xx/5xx 처리)와 `_downloadFeedbackImage`의 캡처 로직은 그대로 둔다. 이번 작업은 표시 계층만 건드린다.

| 상황 | 결과 (기존과 동일) |
| --- | --- |
| 다운로드 미지원 플랫폼 | `UnsupportedError` → "이 플랫폼에서는 이미지 다운로드를 지원하지 않아요" 스낵바 |
| 캡처/변환 실패 | "이미지 다운로드에 실패했어요" 스낵바 |
| 저장 중 네트워크 장애 | 로컬 큐 적재 후 완료 처리 (REQ-009-5) |
| 저장 중 서버 4xx/5xx | 즉시 실패 안내, 완료 처리 안 함 |

**알려진 절충.** 다운로드를 하단으로 올리면 모바일 사용자는 누를 때마다 미지원 스낵바를 보게 된다. 버튼을 숨기거나 비활성화하는 안도 검토했으나, 기능 존재를 알리는 편을 택했다. 작업현황4.md의 "모바일 이미지 다운로드" 항목이 이 부담을 해소하는 후속 작업이다.

## 6. 테스트

**신규**: `frontend/test/widgets/feedback_action_bar_test.dart`

1. 캔버스 모드(`isCanvas: true`)에는 원본 사진 보관 체크박스가 없다
2. 이미지 모드에는 체크박스가 있고, 토글하면 `onConsentChanged(true)`가 호출된다
3. 저장 전에는 `이미지 받기`와 `학습 기록 저장`이 함께 보인다
4. 저장 후(`confirmed: true`)에는 `학습 기록을 저장했어요`와 `이미지 받기`·`홈으로`가 보이고 `학습 기록 저장` 버튼은 사라진다
5. `isConfirming: true`면 저장 버튼이 비활성이고 받기 버튼은 여전히 누를 수 있다
6. `isDownloading: true`면 그 반대
7. 각 버튼 탭이 해당 콜백을 정확히 한 번 호출한다

기존 17개 테스트는 라벨 문자열을 참조하지 않으므로 영향받지 않는다(`grep`으로 확인). 작업 후 `flutter test` 전체를 실행해 확인한다.

## 7. 범위 밖

작업현황4.md 5절의 나머지 항목은 각각 별도 작업으로 남긴다.

- **모바일 갤러리 저장 구현** — android/ios 네이티브 폴더와 권한 세팅이 선행되어야 함
- **캡처 여백 트리밍** — `RepaintBoundary`가 배경 컨테이너(테마 surface 색)까지 캡처하는 문제
- **실기기 캡처 검증** — 웹 환경은 카메라가 없어 회색 placeholder로만 확인됨

## 8. 미해결 안건: 학습 기록 자동 저장

논의 중 "저장 버튼을 없애고 학습 기록을 무조건 저장하자"는 안이 제기되었다. **이번 범위에서는 보류**하고, 백엔드 `confirm` 스펙 확정 시 함께 결정한다.

자동 저장으로 가면 이번 문제(두 요소가 겹쳐 보임)가 근본적으로 사라지고, 사용자가 저장을 잊어 기록이 유실되는 사고도 막힌다. 보류 사유는 이득이 없어서가 아니라 선행 조건이 미비하기 때문이다.

**보류 사유**

1. **`confirm` 엔드포인트가 백엔드에 존재하지 않는다.** 2026-07-25 기준 구현된 엔드포인트는 `login`, `analyze`, `group`, `analyze-detail`, `feedback`(canvas), `preprocess`, `detect`, `analyze`(image), `dashboard`뿐이다. `AppConfig`에 경로만 정의되어 있고 서버 구현이 없어 현재는 mock으로만 동작한다. 자동 저장은 화면 진입마다 호출되므로 멱등성이 전제인데, 스펙조차 없는 상태에서 프론트가 호출 패턴을 먼저 고정하면 백엔드가 그에 맞춰야 한다.

2. **requirement가 명시적 확인 행위를 규정한다.** SFR-007 Post-condition은 "사용자가 피드백을 확인(confirm)하면 SFR-009가 트리거된다"로, 영문 `confirm`까지 병기되어 있다. 자동 저장으로 가려면 이 문구 수정에 대한 팀 합의가 필요하다(작업현황4.md 3절의 requirement 수정 안건과 같은 성격).

3. **REQ-009-4 명시적 동의와 충돌한다.** 이미지 모드의 원본 사진 저장은 명시적 동의가 있을 때만 수행되어야 한다. 진입 시 자동 저장하면 동의 전에 요청이 나가므로 `save_image: false`로 먼저 저장한 뒤 사용자가 체크할 때 두 번째 요청으로 갱신해야 하는데, 그 갱신 API도 정의되어 있지 않다.

**재검토 시점**: 백엔드 `confirm` 엔드포인트 스펙 확정 시. 그때 멱등성 보장 여부와 `save_image` 사후 갱신 가능 여부를 함께 확인한다.
