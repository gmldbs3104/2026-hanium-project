## 3막. 파인튜닝 대장정 — 3번 시도 후 롤백 (2026-07-06 ~ 07-10) ⭐

> 이 프로젝트에서 가장 많은 시간과 교훈이 나온 구간. "우리 손글씨(AI Hub 053)에 맞게 CRAFT를 더
> 특훈시키면 더 정확해지지 않을까?"에서 출발했지만, 세 번 다 기본(pretrained)보다 나빠져 **최종 롤백**.

**🐛 1차 — 학습이 붕괴(collapse)**
- 문제: 학습시키면 아무것도 탐지 못 함.
- 원인: 화면의 99% 이상이 배경이라, 모델이 "전부 배경(0)"이라고 찍어도 점수가 좋아져 버림(극단적 불균형).
- 해결: **OHEM**(어려운 배경만 골라 학습) 도입.

**🐛 2차 — 학습과 실제 입력이 서로 다른 그림**
- 문제: 같은 이미지인데 학습 모델은 65개 vs 3개로 제각각.
- 원인: 학습은 **원본 컬러 사진**, 실제 서비스는 **이진화+deskew+distance-transform**한 그림 → 도메인 불일치.
- 해결: 학습 파이프라인에도 **동일 전처리** 적용.

**🐛 3차 & 결정적 실수 — 잘못된 잣대로 좋은 시점을 골랐음**
- 문제: 학습 중 자체 점수(val_loss)는 좋아지는데 **실제 탐지는 오히려 나빠지는 역전**. peak-weighted OHEM,
  `peak_quality` 지표까지 만들어 재시도했지만 실제 성능과 상관없음.
- **원인(가장 중요)**: 그동안의 모든 검증이 실제 배포 클래스(`CraftDetector`, 기본 threshold 0.7)가 아니라
  **기준을 0.05로 낮춘 별도 스크립트**로 이뤄지고 있었다. 진짜 배포 경로로 재검증하니 모든 체크포인트가
  test_images·AI Hub에서 **전부 0개 탐지**.
- 해결: 파인튜닝 최종 포기, **pretrained로 롤백**(현재 배포 상태).

🔑 **이 구간의 핵심 교훈** — *학습 중 자체 정의한 지표(loss 등)로 좋은 시점을 고르지 말고, **매번 실제
배포 경로(진짜 threshold)로 검증**하라.* 이걸 위해 `debug_compare_production.py`를 만들었다.
🔑 **문서의 "완료" 표시를 액면 그대로 믿지 말 것** — 항상 실제 코드를 직접 확인.
✅ 실패했지만 **학습 파이프라인·구조 통합은 자산으로 보존** — 재도전 시 그대로 재사용 가능(→ [STATUS.md](STATUS.md) §4).

## 4막. 캔버스 모드 — 데이터 없이 시작하기 (2026-07-09 ~ 07-10)

- 캔버스에 필요한 "펜 좌표+시간(온라인 필기)" 공개 데이터셋을 **한국어로는 못 찾음**(AI Hub는 전부 사진).
- 그래서 **규칙 기반 + 합성 데이터** 전략으로 최대한 구현: 획 그룹핑, 표준 획순(11,172자 유니코드 분해로
  자동 생성), 위치 기반 획순 분석, 합성 스트로크 생성기.

🔑 **"제시형 연습이 곧 자동 라벨"** — "이 글자 써보세요: 가"처럼 목표를 미리 아는 UI라, 사용자가 쓴 획에
정답이 자동으로 붙는다. 별도 수집 프로젝트 없이, 배포 후 사용자가 연습하면 학습 데이터가 쌓이는 구조.
🐛 **합성 데이터 지터 버그** — 노이즈를 정규화 좌표([0,1])에 더한 뒤 스케일링해서 **100배 증폭**됐음.
스케일링 **후에** 지터를 더하도록 수정. (좌표 변환 순서 주의)
🔑 LSTM(진짜 학습 모델)은 실데이터가 있어야 가능 → 지금은 **정직하게 스텁**으로 두고, 위치 기반 근사치가
실질 동작을 대신함.

## 5막. 탐지 품질 재진단 & 정량 평가 도입 (2026-07-13 ~ 07-18)

- **"파인튜닝 없이" 탐지를 끌어올린다**는 원칙으로, 먼저 **음절 단위 평가셋 + F1 측정 파이프라인**을 구축.
- 개선을 단계로 쪼개 진행(1~14단계): region 단독 디코딩(link=1.0)으로 단어 병합 방지, 적응형 long_size,
  과폭 박스 분할, 자소→음절 병합, 행 그룹핑/병합 오작동 수정, region 피크 기반 근접 2음절 분할 등.
- ✅ 실사용 유사 3~4장 평균 **F1@0.3 ≈ 0.97**까지 상승. `ai` 패키지화 + 백엔드 어댑터 실구현 연동.

🐛 **평가가 전부 0.000 나오던 함정** — AI Hub GT 좌표계 스케일 보정을 빼먹어서. 좌표계는 항상 맞춰야.
🔑 **개수 비교는 착시** — "예측 수/정답 수"는 좋아 보여도, 박스 위치 정렬(F1)은 낮을 수 있다. IoU 0.3·0.5 병행.
🔑 **소형 밀집 글씨는 확정된 한계** — 모델이 그 스케일에서 아예 반응 안 해 후처리로 복구 불가. GPU 초고해상도/
타일링만 남음.

## 6막. 평가 기준 정교화 (2026-07-19)

- 기울기 측정을 minAreaRect → **세로획 slant(HoughLinesP) + 신뢰도 게이트**로 교체, 문서 단위 평가로 전환.
- **GT 2차 검수**: 제3자 검수에서 139자 중 24건(≈17%) 오류 발견·교정. 평가 지표 ①~⑥ 전면 구현 + 명료도 감점.
- 지표 ⑦(자소 내부 비율)은 "모드 목적과 불일치"로 **제외 확정**.

🔑 **정답지(GT)도 틀린다** — GT는 "만들고 끝"이 아니라 검수 라운드로 수렴시킬 대상. 탐지기 초안으로 만든
GT는 탐지기의 실수를 물려받는 **순환성**이 있어, 독립 라벨이 필요.

## 7막. 설계 인터뷰 & 규범 축 도입 (2026-07-20 ~ 07-21)

- 인터뷰로 방향 확정: 이미지 모드 = **자유 촬영**(OCR 없음, 자기 일관성 + 절대 규범), 종합점수 = 교육적
  가중(정렬·균일 3:2:1), 명료도는 경고만, 캔버스 획순은 복수 정본.
- 구현: **절대 규범 축**(기울기 수직 이탈 / 자간 띄어쓰기 뭉개짐 / 행간 줄 겹침) — 자기 일관성과 별개 축,
  감점 없이 경고만. 종합점수 가중화 + 명료도 경고화. 규범 임계값은 필기 교본·조판 문헌으로 근거 확보.

🔑 **"고르게 썼는가"(자기 일관성)와 "형식에 맞는가"(절대 규범)는 다른 축** — 둘을 분리해 병렬 표시.

## 9막. 평가셋 확장 — 흘림 3장 독립 GT 라벨링 (2026-07-23)

- **test4(239음절)·test5(39)·test7(62) 수동 라벨링 완료** → 평가셋 4장(197음절) → **7장(537음절)**.
  통합 전 "가장 레버 큰" 작업(평가셋·독립 GT)을 먼저 처리한 것.
- **독립 GT 원칙 준수** — 탐지기 출력을 초안으로 쓰지 않고, connected component blob 추출 →
  사람이 음절 단위 그룹핑(`label_helper.py` 기존 절차). 기존 GT의 순환성 문제를 새 라벨에는
  만들지 않음.
- **흘림 라벨링의 난제 해결** — 흘림은 한 획이 음절 경계를 넘어 이어짐(예: test5 "하세"의
  ㅏ→ㅅ, test4 "우리빈"류 다음절 연결 blob 60여 개). `label_helper.py`에 **blob 분할 기능**
  추가: groups.json의 `"splits"`에 x좌표(세로 절단)·y좌표(가로 절단)·격자(x+y)를 지정하면
  잉크 픽셀 기준 tight bbox로 조각냄. 하위 호환 유지(기존 groups 형식 그대로 동작, 회귀 확인).
- **판독 방법** — blob별 픽셀을 색으로 칠한 확대 렌더링으로 blob↔자소 소속을 눈으로 확정
  (스크래치 스크립트). 애매한 곳은 원본 사진 crop과 대조 — 이 과정에서 test4 12행이 "곧 다시"가
  아니라 **"금방 다시"**임을 확인(글자 수가 달라지는 오독을 원본 대조로 잡음).
- **GT 관례 확정** — 문장부호(마침표·쉼표·?·!)는 음절이 아니므로 제외(기존 GT도 면적 필터로
  사실상 제외돼 있었음). 영문("TEST")은 글자별 1박스. 매직펜 윤곽선 이진화의 내부 윤곽 blob은
  해당 음절에 포함(bbox 불변).
- **2차 검수(같은 날)** — 팀 검수에서 test4 박스 60여 개 지적받아 전면 재판독. 원인은 대부분
  다음절 연결 blob의 **절단 위치를 눈대중(글자폭 등분)으로 정한 것**: 받침이 옆 음절로 넘어가거나
  ('합니'의 ㅂ, '깁니다'의 ㅂ/니 혼동), 자모 기둥이 잘리는('유'의 ㅠ 둘째 기둥) 오류. 재작업은
  **blob별 세로 잉크 프로파일(열별 픽셀 수)의 골짜기**를 기준으로 절단 위치를 정하고, 전 구간을
  GT 오버레이 렌더링으로 재검증. '복'의 ㄱ 장식 꼬리(13행 관통)는 박스 왜곡 방지 위해 GT에서 제외.
- ✅ **결과** — 확장 7장 평균 **F1@0.3 0.938 / F1@0.5 0.894** (기존 4장 0.968/0.946).
  흘림 개별: test4 0.902(ratio 0.83 과병합), test5 0.873, test7 0.927. 테스트 29개 통과.
  (test7 '노트': 흘림으로 '노'와 '트'가 한 blob으로 이어져, 왼쪽=노·오른쪽 긴 가로획=트의 ㅡ 밑변으로
  분할. 처음엔 그 가로획을 '노의 ㄴ 밑변'으로 오판해 제외했다가, 사람 검수에서 '트에 ㅡ가 없다'는
  지적으로 트에 재배정 — GT는 사람 판독이 최종 기준임을 재확인.)

🔑 **평가셋에 어려운 케이스를 넣어야 진짜 성능이 보인다** — 흘림 3장을 넣자 평균이 0.968→0.938로
내려왔다. 내려간 게 나쁜 게 아니라, 이전 수치가 쉬운 표본의 상방 편향이었던 것.
🔑 **"라벨링 불가"는 도구 문제였다** — 흘림 라벨링이 어려웠던 건 blob이 음절을 넘기 때문이고,
분할 도구를 만들자 해결됐다. 막힌 작업은 원칙(독립 GT)을 깨지 말고 도구를 보강할 것.
🔑 **절단 위치는 눈대중이 아니라 데이터로** — 글자폭 등분 추정은 2차 검수에서 무더기로 걸렸다.
잉크 프로파일 골짜기 + 오버레이 재검증으로 바꾸자 재현 가능하고 반박 가능한 근거가 생겼다.
GT도 코드처럼 리뷰(검수 라운드)가 필요하다 — 6막의 "정답지도 틀린다" 교훈 재확인.

**브라우저 라벨링 GUI로 도구화** — 위 방식은 매번 스크래치 렌더링 스크립트를 짜고 AI가 확대 이미지를
판독해야 해서, 장당 비용이 크고(토큰) 흘림에선 AI 오독 위험도 남았다. 그래서 `eval/label_gui.py` +
`label_gui_template.html`로 **사람이 브라우저에서 직접 클릭**해 blob을 음절로 묶고 분할선을 긋는 GUI를
만들었다: 결과는 `groups.json`으로 떨어지고 기존 `label_helper.py build`가 그대로 받는다.
**AI가 이미지를 판독하지 않으므로 토큰을 거의 안 쓰고**, 판독은 사람이 하니 흘림도 정확하다.
우클릭=기존 음절 선택(재수정), Enter=새 음절, "기존 groups.json 불러오기"로 검수 라운드를 돌릴 수 있다.
조각 이름 규칙이 `label_helper._split_blob`과 100% 일치하는지 검증까지 마쳤다.
절차·관례는 `.claude/skills/gt-labeling/SKILL.md`(skill)로 고정해, 다음 라벨링이 같은 규칙을 따르게 했다.

🔑 **비용 구조를 바꾸면 작업의 성격이 바뀐다** — "AI가 판독 → 사람이 검수"에서 "사람이 판독 → 도구가 기록"
으로 뒤집자, 정확도(흘림 오독)와 비용(토큰) 문제가 **동시에** 사라졌다. AI에게 시킬 일과 사람이 해야 할
일을 나누는 게 프롬프트를 다듬는 것보다 효과가 컸다.

**merge/split 분리 측정 추가** — `evaluate_detection.py`에 과병합·과분할을 따로 세는 지표
(`count_merge_split`). F1·count_ratio 하나로는 두 오류가 상쇄돼 안 보이던 게 드러났다:
test3_crop은 ratio 0.95(거의 완벽처럼 보임)인데 실제로는 **분할 9 + 병합 14**가 부분 상쇄된 것,
test4는 ratio 0.83이 "약간 병합"이 아니라 **병합 43 / 분할 5**로 압도적 과병합이었다. 깔끔한
test·test6은 0/0으로 sanity check 통과. 앞으로 후처리를 손볼 때 "병합을 줄였나 분할을 늘렸나"가
이 두 수로 바로 보인다. (겹침 판정은 IoU≥0.3 또는 작은 박스 포함비율≥0.6 — 작은 조각이 큰 박스에
들어가는 경우 IoU만으론 놓치므로 포함비율 병용.)

🔑 **집계 지표는 오류를 상쇄해 숨긴다** — count_ratio가 1.0이어도 병합·분할이 동시에 진행 중일 수
있다. 개선을 측정하려면 오류를 종류별로 분리해서 봐야 한다(6막 "개수 비교는 착시"의 정량화판).

**순환성 편향 측정(test3_crop)** — 오래 "기존 4장 GT는 탐지기 초안 기반이라 순환성(상방 편향)이
있다"고 경계만 해왔는데, 실제로 쟀다. test3_crop(가장 크고 우려 컸던 줄글)을 GUI로 **독립 재라벨링**
(탐지기 초안·기존 GT 안 보고 blob부터)한 뒤 기존 GT와 비교: 두 GT 상호 평균 IoU **0.992**(140쌍 중
129쌍 IoU>0.99 — 불러오기 아닌 진짜 독립인데도 거의 일치), 탐지 F1도 어느 GT로 채점하든 차이 ≤0.007.
→ **이 이미지의 순환성 편향은 사실상 0.** 결론: 기존 4장을 다시 만들 필요 없고, 7장 통합 평균을 그대로
써도 왜곡이 없다. 4장(0.968) vs 3장(0.87~0.93) 격차는 순환성이 아니라 흘림 난이도 차이.

🔑 **의심은 측정으로 닫는다** — "순환성이 있을 것"이라는 합리적 우려도, 재보니 이 케이스에선 0이었다.
또박또박한 글씨는 탐지기 초안이 정확해 물려받을 실수가 애초에 적다(순환성은 탐지기가 틀린 곳에서만
생긴다). 흘림 3장은 어차피 독립 라벨링했으니 무관. 경계하던 편향을 문서에 "있다"로만 두지 말 것.

## 11막. 이미지 전처리 개편 — 측지 재구성 + close 버그 + A방향 리사이즈 (2026-07-25 ~ 07-27)

> `IMAGE_PIPELINE_REBUILD_PLAN.md`(07-24)를 실행한 구간. T1(전처리 재작성)·T2(크래시)를 반영하고,
> **리사이즈 정책과 보존율 게이트는 A/B/C 실측으로 확정**했다. 이 막에서 8막의 "리사이즈 유지가 정답"
> 결론이 **부분적으로 뒤집혔다**(근본 원인이 리사이즈가 아니라 close 버그였음). 문답을 상세히 남긴다.

### 무엇을 했나 (요약)
1. **전처리를 측지 재구성으로 재작성(T1)** — 채널 max 그레이 → 조명 정규화(division) → 잉크 후보량 기반
   적응형 seed/mask → 150회 측지 팽창 재구성 → 획 강도 정규화 → 보존율 게이트 → close → 소형 노이즈 제거.
   adaptiveThreshold(국소 대비만 봐 비침·괘선을 진짜 획으로 승격)를 버린 이유이자, 비침을 **원천 제거**하는
   방식. 공개 API(`preprocess_from_file/bytes/base64`)·`PreprocessResult` 계약은 유지.
2. **탐지 크래시 수정(T2)** — 아래 🐛.
3. **리사이즈·게이트 정책 확정** — 아래 문답·🐛.

### 🐛 close 방향 버그 — 획 43% 소실 (이 막의 핵심)
- **문제**: 측지 재구성으로 바꿨더니 data/(AI Hub 태블릿 손글씨 25장, 글자 높이 ~12px)에서 글자가
  **점선처럼 깨져** 판독 불가. 사용자가 시각화(`hanium_out/05_전처리검증`)를 보고 지적.
- **원인**: 마무리 `close`를 `cv2.morphologyEx(fg, MORPH_CLOSE, 3×3)`로 걸었는데, `fg`는 **검은 잉크/흰 배경**
  이라 이 연산은 **밝은 배경을 close** → 팽창-침식이 가는 획을 깎아 끊는다. 격리 실측(`06_close검증`):
  close 없음 60,694px → **현행 close 34,972px (−43%)**. 확대하면 "정부가 올해"가 점 파편으로 붕괴.
- **해결**: 잉크 전경을 close하도록 반전 — `255 - cv2.morphologyEx(255 - fg, MORPH_CLOSE, 2×2)`.
  같은 이미지 61,607px로 원 재구성을 보존(+약간 연결). 이게 dmack `craft_preprocess (1).py`의 수정과 동일.
- **파급**: 이 버그 위에서 A/B/C 리사이즈를 비교했던 초기 결론("C가 낫다")이 **오염된 것**이었다(아래 문답 ①).

### 🐛 T2 — 풀해상도 탐지 크래시 (`poly=True`)
- **문제**: 풀해상도(long_size 2560) 탐지 시 `craft_utils.adjustResultCoordinates`의 `np.array(polys)`가
  **가변 길이 폴리곤** 때문에 `ValueError`(inhomogeneous shape). C(1600)에선 재현 안 되다 A(풀)에서 터짐.
- **원인**: `detect_text`가 기본 `poly=True`로 `get_prediction`을 불러 폴리곤을 만드는데, 우리는
  `crop_type="box"`라 폴리곤을 **쓰지도 않으면서** 그걸 만들다 터진다.
- **해결**: `_craft_prediction`에서 `detect_text` 대신 `get_prediction(..., poly=False)` 직접 호출.
  박스 결과는 poly 값과 무관하게 동일(검증: 패치 유무 149자=149자). 손실 0.

### 문답 ①  "리사이징이 가장 큰 문제 같다. 원본 그대로 쓰는 게 낫지 않나? A/B/C 분석해줘"
개선된 프롬프트로 **A(풀해상도)·B(glyph-aware 축소)·C(고정1600, 현행)** 를 25장(data/) + 7장(test_images,
char-GT) 실측 비교했다. **당시엔 close 버그가 살아 있었다.**
- **용량은 비제약**: 출력이 2색 이진이라 풀해상도 PNG ≈26KB로 원본 컬러(≈130KB)보다 **작다**. "용량 때문에
  줄여야 한다"는 전제가 애초에 틀림.
- **CRAFT는 해상도에 둔감**: `adaptive_scale`가 glyph 크기로 long_size(2560)를 정해 A/B/C 모두 같은 크기로
  재리사이즈. 관건은 "재리사이즈 전에 획 정보가 살아있나".
- **깨진 base에서의 결과**: C(0.561) > A=B(0.379) — C의 축소-재이진화가 **깨진 획을 두껍게 메워** 유리해 보임.
  → 그래서 처음엔 "C 유지"로 결론 냈다. **이게 오판**이었다(close 버그가 세 방식 모두를 깨뜨린 상태였음).
- **close 고친 뒤 재측정**: A(0.988) ≈ C(0.995)로 **동률**. C의 우위는 사라졌다. 사용자가 "리사이즈 문제가
  아니라 (1)을 반영하니 정상이더라"고 지적해 근본 원인(close)을 찾은 것이 결정적이었다.
- test_images(글자 큼) F1: close 전후 모두 A≈B≈C ±0.01로 **차이 없음**. 큰 글자는 애초에 리사이즈에 둔감.

### 문답 ②  "이전(adaptiveThreshold) 버전이 획을 덜 지웠는데 장점을 합칠 수 없나?"
- **검증**: 이전 버전은 획 보존은 되지만 **괘선·비침을 승격**(test_line1 잉크 9.5% vs 신규 6.0%, 오버레이에
  괘선이 텍스트를 관통 — `08_Q1_old_vs_new`). 신규는 비침 제거는 되지만 close 버그로 획을 깎았다.
- **답**: **close를 고친 신규 버전이 이미 둘을 합쳤다** — 획 보존(이전의 강점) + 비침/괘선 제거(신규의 강점).
  별도로 합칠 게 없다. 사용자 관찰("이전이 획 덜 지움")은 맞았지만 그건 신규의 **버그** 때문이었고,
  버그를 고치니 격차가 사라진다. NEW-fixed가 OLD를 지배.

### 문답 ③  "전처리 출력이 사용자 손글씨에 가장 비슷해야 하지 않나?(교정 앱이니까)"
- **핵심 통찰(사용자)**: 전처리 이진은 탐지뿐 아니라 **분석(교정 피드백)** 의 입력이므로 원본 획에
  충실해야 한다 → 최적화 목표가 "탐지 F1"이 아니라 "손글씨 충실도"로 바뀐다.
- **실측으로 판정**: 유지 지표(크기 균일=높이 CV, 자간·행간·기준선 CV, 문장 기울기=각도)는 전부 **비율·각도
  기반이라 균일 스케일에 불변**. GT 박스를 ×1.0/0.456/0.30으로 스케일해도 지표 **완전히 동일**(극단 0.30만
  절대 픽셀 명료도 필터로 미세 변동). → **C의 축소·획 두꺼워짐은 유지 지표를 왜곡하지 않는다**(획 두께 지표는
  이미 제거했으므로 두꺼워짐 무관).
- **그런데도 A를 택한 이유**: close를 고치니 **A(풀해상도)가 C와 탐지 동률**이 됐다. 이전엔 A를 쓰면 탐지가
  나빠졌지만 이제 아니다. 즉 **충실도(A)를 공짜로 얻을 수 있게 됐다** → 앱 목적(손글씨 평가)에 A가 가장 맞음.
  "탐지용/분석용 입력 분리"는 불필요(풀해상도 하나가 둘 다 만족).

### 문답 ④  "보존율 게이트 (1)식 반영 vs 미반영 비교해줘"
- **동작 차이**: test_images 14장 전부 동일(게이트 미발동). data/ 25장 중 **10장**에서 (1)게이트(coverage)가
  recon→stretch 폴백을 택함.
- **품질(차이 10장)**: 단어 재현율 **0.994 = 0.994 동률**. 하지만 (1)게이트가 글자를 더 잡고(faint 복구),
  **육안(`09_게이트비교`)에서 04399의 "세계적으로"를 현행이 놓친 걸 (1)게이트가 되살림**(실제 획, 노이즈 아님).
- **비침 안전성**: 합성 비침에서 둘 다 recon 유지·비침 0px. (1)게이트의 `fer`(옅은대역 제거 증거) 조건이
  비침 이미지에선 recon을 유지시켜 비침 제거를 희생하지 않는다. → **안전한 소폭 개선으로 채택**.

### 최종 반영 (프로덕션, 미커밋 → 이 세션에서 커밋)
- **close**: `255-CLOSE(255-fg, 2×2)` (잉크 전경 close) — 필수.
- **resize**: **A방향** — 다운스케일 상한 제거, 원본 해상도 유지, 장축<800만 업스케일. (1)의 glyph-aware(B)는
  data/에서 C에 열세라 미채택.
- **게이트**: (1)식 coverage 게이트(percentile→coverage, 폴백 lo=90). 연한 획 복구 + 비침 유지.
- **T2**: `poly=False`. (1)엔 없는 우리 탐지기 자체 수정.
- 단위 테스트 32개 통과(비침 억제 포함), 프로덕션 경로에서 풀해상도 탐지 크래시 없음·재현율 0.99대 확인.

🔑 **오염된 베이스라인 위 비교는 무효** — A/B/C를 "깨진 close" 위에서 재고 "C가 낫다"고 결론냈지만,
근본(close)을 고치니 뒤집혔다. 여러 안을 비교하기 전에 **공통 전제(재구성 품질)가 성한지** 먼저 확인해야 한다.
버그를 먼저 못 찾은 건 사용자가 "(1)을 반영하니 정상"이라 짚어준 덕에 교정됐다.
🔑 **이진 형태학은 극성이 결과를 뒤집는다** — `CLOSE(fg)`와 `255-CLOSE(255-fg)`는 완전히 다른 연산이다.
잉크가 밝은지 어두운지(전경/배경)에 따라 close가 획을 잇기도, 깎기도 한다. 부호를 항상 명시적으로 검증할 것.
🔑 **포화된 지표는 개선을 숨긴다** — 단어 재현율이 0.994로 saturation돼 게이트의 "연한 획 복구"를 못 잡았다.
글자수 + 육안 크롭이 그 차이를 드러냈다(9막 "집계 지표는 오류를 상쇄해 숨긴다"의 재판 — 이번엔 포화판).
🔑 **충실도 우려는 지표 민감도로 판정** — "축소하면 손글씨와 달라진다"는 시각적으론 맞지만, 실제 유지 지표가
스케일 불변이면 무영향이다. 걱정을 측정(스케일별 지표 비교)으로 닫았고, 그 결과 A가 "공짜 충실도"임이 드러났다.
🐛 **측정 함정 3종** — (a) data/ 스윕에서 C를 `_resize(A)`(블롭 제거 순서 다름 = Ca)로 만들어 실제
프로덕션 C(Cb)보다 약하게 측정(97 vs 149자) → 결론 방향은 무관했으나 절대치가 왜곡됐음을 격리로 확인.
(b) 탐지가 실행 순서에 영향받는 듯 보였으나 실은 (a)의 이미지 구성 차이였음(패치 유무·반복은 결정론적).
(c) GT 좌표계는 리사이즈-ON 공간 → 변형별 배율 역변환 필요. **재보기 전에 원인을 규명**(9막·10막 교훈 연장).

### 문답 ②  "문장 기울기, 수정이 필요한 건가 이미 된 건가?"
- **판정(확정)**: **이미 됨. 코드 수정 불필요.** `handwriting_analyzer.py`에 `_sentence_tilt`(행별 중심선
  회귀)가 들어와 있고 옛 `_tilt`·`_stroke_width`는 삭제됨. 좌표는 **전처리 이미지 그대로**(skew 역회전 안 함).
- **주의(문서-코드 어긋남)**: 계획서 T4는 "skew_angle로 역회전(deskew 이전 좌표)"을 적어놨지만 **실제 코드는
  반대**(코드 주석 "전처리 이미지 좌표에서 측정 — 사용자 결정"). 이전 세션의 사용자 결정이 계획서에 역반영 안 됨.
  → 코드가 정답, 계획서가 stale. 문서 정정은 일괄 정리 때.

### 문답 ③  "우선순위 #1(후처리 과최적화)부터 진행해줘"  — 홀드아웃 렌더가 뭘 한 건가
- **목적**: 탐지 **후처리 규칙**(과폭 분할·자소→음절 병합·CC 박스 완성·적응형 long_size)이 평가셋 7장에만
  맞춰진 **과최적화**인지 확인. 방법(STATUS §1): 라벨 안 된 홀드아웃(test8~10·test_line1~3)에 후처리
  **on/off** 박스를 나란히 렌더 → 사람이 "새 사진에서 규칙이 이상한 짓을 하나"를 눈으로 판정.
- **문제**: 탐지기에 후처리를 끄는 플래그가 없다(`detect()` 안에 함수 호출로 박혀 있음).
- **해결**: 프로덕션 코드를 안 건드리고, 디버그 스크립트에서 모듈 함수 3개(`split_wide_boxes`·
  `merge_jaso_boxes`·`complete_boxes`)를 **임시로 항등함수로 우회(monkeypatch)** 해 raw CRAFT 박스를 뽑았다.
  적응형 long_size는 양쪽 동일하게 둬서 **후처리 효과만 격리**. 스크립트: `debug_holdout_postproc.py`.
- **결과(1차, 개수)**: 6장 전부 후처리가 박스를 **줄인다**(자소 병합 우세). test8 110→99,
  test_line1 312→250 등. **폭발적 유령 박스 없음** = 일단 나쁜 신호 아님. test9·test10은 초광각이라
  전처리가 **RETAKE(재촬영)** 로 분류(정상 동작). test_line(줄노트 괘선) 건도 이 렌더로 같이 확인 가능.
- **육안 1차 판정(사용자)**: ON·OFF **둘 다** 오병합/오분할이 남아 있으나 **ON이 더 낫다**. → 후처리 규칙이
  평가셋 밖 새 사진에서도 개선으로 작동 = **과최적화 우려 상당 부분 완화**(개발셋 과적합이 아님).
- **델타 오버레이 판정(Claude 육안 + 사용자)**: OFF(회색)+ON(빨강+char_id) 겹쳐 그린 `*_overlay.jpg`로
  test8·test_line1·test_line3 확인 — ON 박스가 **음절 단위로 깔끔**, **괘선 위 유령 박스 없음**(줄노트
  전처리 OK), **두 글자 통짜 오병합 없음**. 사용자가 본 오병합/오분할은 **OFF·ON 양쪽에 있어 CRAFT 원본에서
  온 것**(후처리가 새로 만든 (b) 오류가 아님) = 흘림·붙여쓴 2음절 등 기존 탐지 한계 (a). 경미한 과분할(겹치는
  박스) 소수뿐.
- **결론**: 후처리 규칙이 **개발셋 밖 새 사진에서도 도움·무해** → **과최적화 우려 육안상 종료**(STATUS §1의
  🟡 "후처리 과최적화 미측정"을 육안 근거로 완화 가능). ⚠️ 단 **육안≠정량** — 새 파이프라인 F1은 T5(GT 재라벨)
  →T7 필요. 홀드아웃 GT를 만들면 이 판정을 수치로 확증하게 된다.

🔑 **과최적화는 "새 오류를 만드나"로 본다** — 후처리 on/off를 새 이미지에 겹쳐, 오류가 양쪽 공통(모델 한계)인지
ON에서만 새로 생겼는지(과적합 손상)를 갈랐다. 개수·집계가 아니라 **델타(무엇이 바뀌었나)**가 판정의 핵심.

### 문답 ④  "회색 박스(raw CRAFT) 자체가 틀린 건 개선 불가능한가?"
후처리는 **이미 잡힌 박스를 정리**할 뿐이라 오류 유형별로 다르다. **과분할→병합으로 해결(✅ ON), 비침·괘선
유령→전처리로 해결(✅)**. 그러나 **두 음절 붙여 씀**(잉크 골짜기 없어 기하만으론 못 나눔 — 읽어야 풀림, 이미지
모드엔 OCR 없음)과 **아예 안 잡힘**(소형 밀집·연한 획에 모델 무반응 — 없는 걸 못 만듦)은 후처리 불가 = STATUS §1
확정 한계. raw CRAFT **자체**를 올리는 레버는 후처리 밖: 전처리(이미 함)·threshold 완화(유령과 트레이드오프)·
**도메인 파인튜닝**(진짜 해법이나 3회 실패, §4 조건부 재도전)·다른 탐지기(범위 밖). → **파인튜닝 값어치는 새
파이프라인 F1이 나와야 판단** = T5→T7이 그 선행. (이 문답이 T5 준비 착수의 직접 동기.)

### 첫 새 파이프라인 F1 — test8 (홀드아웃) ⭐
사용자가 test8을 GUI로 라벨 → blobs(136개)→build(음절 GT **106개**, 8개는 문장부호/노이즈 제외)→evaluate.
**전 과정(label→blobs→build→evaluate)이 도는 것을 처음 검증.** 격리 평가(옛 파이프라인 GT 7장은 좌표계가
달라 잠시 옆으로 옮기고 test8만 평가 후 복원).
- **결과: F1@0.3 0.898 / F1@0.5 0.780 / R@0.3 0.868** (pred 99, gt 106, ratio 0.93, **merge 12**·split 2).
- 옛 파이프라인 7장 평균 0.938(@0.3)과 유사하나, **test8은 개발에 안 쓴 홀드아웃**이라 오히려 **더 정직한
  일반화 수치**다(옛 0.938은 개발셋=테스트셋). 즉 측지 재구성 재작성 뒤에도 일반화 F1@0.3≈0.90 유지.
- 오류는 **merge 12 우세**(pred<gt) = 붙여쓴/흘림 **과병합** — STATUS §1 확정 한계이자 이번 육안 델타 판정과
  일치(후처리가 새로 만든 오류 아님). 🔑 **홀드아웃 수치가 dev=test 수치보다 신뢰도 높다**: 0.898<0.938이지만
  전자가 더 믿을 값.
- ⚠️ **1장 표본** — 확정 아님. test_line·재라벨 7장으로 확대해야 평균이 의미를 갖는다.

### 🐛 새 전처리가 연한 획을 통째로 지운다 (test7·test5, T5 라벨 중 발견 — 중대)
- **증상**: 사용자가 test7 라벨 GUI에서 "글자가 많이 사라졌다", test5도 음절 1개 소실 보고.
- **격리**: `debug_preprocess_stages.py`로 단계별 덤프. `02_ink`(정규화 잉크)엔 '만들어서'·'아는데'가
  다 있으나 `05_recon`(측지 재구성 후)에서 소멸 → **재구성 단계가 원인**. 진한 획('이걸 어찌 해야할지',
  'TEST 자료가')은 완벽 보존 = **손실이 획 진하기에 비례**.
- **근본 원인**: seed = 잉크 강도 상위 ~1%(가장 진한 것만). 연한 음절은 **자기 seed가 없고** 진한 획과
  떨어져 있어, mask엔 있어도 seed dilation이 닿지 못해 재구성에서 제거됨 — **비침 제거 메커니즘이 연한
  실제 글씨를 비침으로 오인**. seed 기반 측지 재구성의 근본 트레이드오프.
- **게이트가 왜 못 잡았나**: coverage 게이트는 강한 획(norm<110) 커버율(cov0)만 본다(test7 cov0=1.0 →
  recon 채택). 연한 음절은 faint 대역(110-190)이고 fer=0.072(집계)라 통과 — **국소 음절 통째 소실을
  집계 지표가 못 봄**(9·11막 "집계가 오류를 숨긴다" 재판, 이번엔 전처리판).
- **파급**: test7·test5뿐 아니라 **연하게 쓴 실제 사용자 글씨를 서비스가 지운다** = 교정 앱에 치명적.
  또 이 위에서 만든 GT(test8·test·test2·test5)와 F1(test8 0.898)은 **연한 글씨 소실을 포함한 전처리**
  기준이므로, 전처리 수정 후 **재라벨·재측정 필요**(지금 값은 잠정).
- **상태**: 근본 원인 확정(Phase 1~2 완료). 수정은 **seed 기반 재구성의 트레이드오프**라 방향을 사용자와
  논의 후 구현(systematic-debugging Phase 4.5). **T5 라벨링은 이 수정 후 재개**(지워진 글자는 라벨 불가).
- **수정 시도 ① 성분-seed(intensity) → 벽**: 사용자가 '성분 단위 seed' 채택. 실측(`debug_seed_measure.py`):
  연한 실제 글씨 peak(test7 143·test5 126)와 **실제 비침(test_line 상위 ~190)이 절대·상대(둘 다 ~0.76) 모두
  겹침** → 세기로 구분 불가. 엣지 sharpness도 실패(test7 연글씨 1.5~2.4 < test_line 버림성분 3.4~3.7,
  괘선 혼입으로 방향 역전·이미지 내 유지/버림도 겹침).
- **더 깊은 원인(재프레이밍)**: test_line은 진짜 글씨가 매우 진해(peak 250+) 노이즈(<194)와 **틈이 큰 이봉**
  → 높은 seed 임계가 정확히 갈라냄. test7은 진한 앵커 없이 **진→연 연속** → 같은 임계가 연한 진짜 글씨를 자름.
  ⇒ 판별 신호는 **성분별 특징이 아니라 "이미지별 히스토그램 성질"(이봉+틈 vs 연속)**. 성분-seed 접근 폐기,
  **이미지별 라우팅**(이봉+틈=geodesic 안전 / 연속=gentle로 연한 글씨 보존)으로 방향 전환 논의.

### ✅ 수정 — 이미지별 라우팅(진한 앵커 유무), 우선순위=연한 글씨
- **사용자 방침**: 연한 글씨 최우선. 실사용자는 clean 종이에 테스트를 쓰므로 비침은 드묾 →
  비침을 못 잡아 유령 박스가 나오면 차라리 "깨끗한 종이에 다시 찍으세요"가 낫다.
- **구현**(`_reconstruct_ink` upfront 라우터): `frac_black`=잉크 픽셀 중 near-black(세기≥`INK_BLACK_LEVEL`=220)
  비율. `< BLACK_ANCHOR_FRAC`(=0.02)면 **gentle**(선형 스트레치, 연한 글씨 보존), 아니면 **geodesic**(비침 제거).
  근거: 연한 글씨(test7 143·test5 126)와 비침(test_line ~190)은 **세기로 구분 불가**하나, "진짜 글씨가
  진한가(near-black 앵커 존재)"는 이미지 단위로 갈린다.
- **실측 라우팅(전 세트 일치)**: gentle = **data/ 25장** + test·test4·test5·test6·test7 (frac_black **0.000**);
  geodesic = test8·test3_crop·test_line1~3·test2 (0.036~0.693). 0.02가 틈 정중앙. ⭐ data/ 25장 전부 gentle =
  사용자가 우려한 "data/ 글씨 날아감"도 이 수정으로 해결(geodesic이 버리던 04399 등 연한 획 보존).
- **검증**: 단위 테스트 **34개 통과**(신규 2 — gentle/geodesic 라우팅). 실제 파이프라인 test7 이진에서
  '만들어서'·'아는데' 등 연한 음절 **전부 복원(육안)**; test5·data 04399 보존; test8·test_line 비침 제거 유지(geodesic 불변).
- **GT 영향**: gentle 이미지는 전처리 출력이 바뀜 → **재라벨 필요**(이미 만든 것 중 test·test5). geodesic
  이미지는 출력 불변 → **GT 유효**(test2·test8). test8 첫 F1 0.898은 geodesic이라 유효. **gentle 이미지 라벨
  GUI 재생성**(옛 GUI는 geodesic 출력 기준). T5 재개는 재생성 후.
- 🔑 **구분 불가는 경계를 올려서 푼다** — 연한 글씨≡비침을 픽셀/성분에서 못 가르면, 판단을 **이미지 단위**로
  올린다(앵커 유무). 낮은 층위에서 안 되는 분류는 상위 맥락에서 되기도 한다.
- ⚠️ 미구현(STATUS로): 비침 gentle 통과 시 유령 박스 → "깨끗한 종이 재촬영" 안내(탐지/품질 단계).

## 지금까지의 핵심 교훈 6가지 (요약)
1. **실제 배포 경로로 검증하라** — 자체 지표(loss·커스텀 threshold)는 실제 성능과 어긋날 수 있다.
2. **정답지도 의심하라** — GT 오류·순환성은 상방 편향을 만든다. 검수와 독립 라벨이 필요.
3. **직관은 측정으로** — 리사이즈·전처리 판단 모두 실측이 뒤집었다(단, 오염된 베이스라인 위 측정은 무효 — 11막).
4. **근거 없으면 넣지 않는다** — 획순 대안처럼, 확실한 근거만 반영하고 나머지는 확장 여지로.
5. **정직하게 스텁으로** — LSTM은 데이터 없이 가짜 구현하지 않고, 근사치가 대신하되 한계를 문서화.
6. **근본을 먼저 고치고 비교하라** — 여러 대안을 비교하기 전에 공통 전제가 성한지 확인. 깨진 close 위의
   A/B/C 비교는 오판을 낳았다. 포화·상쇄되는 집계 지표는 개선을 숨기니 육안·분해 지표를 병행.
