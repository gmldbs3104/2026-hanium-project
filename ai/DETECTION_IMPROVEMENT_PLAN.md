## 1. 재진단 — AI 파트의 실제 문제점 (심각도 순)

### P1. 탐지가 "음절 단위 정확 분리"가 안 됨 — 핵심 요구사항 미해결

요구사항(REQ-005I-2)은 글자별 크기/기울기 분석을 요구하는데, 현재 pretrained CRAFT 출력은:

- AI Hub 이미지: 정답 대비 112~119% **과분할** (자소 단위로 쪼개짐)
- test.jpg: 10글자 → 8박스. 시각화로 직접 확인한 결과 "한이", "두둥"이 각각 한 박스로
  붙은 **과병합**

즉 글씨가 작으면 자소로 쪼개지고, 크면 인접 음절이 붙는다 — 방향이 일정하지도 않다.
박스가 틀리면 SFR-005I 분석이 전부 왜곡된다(쪼개진 자소 → "작은 글자" 오판, 붙은 두 음절
→ "큰 글자" 오판). test.jpg의 `size_uniformity_score = 3.9`라는 극단적 저점수도 실제
글씨 문제가 아니라 박스 오류의 산물일 가능성이 크다.

**파인튜닝 롤백은 적절했지만, 롤백은 "해결"이 아니라 "원점 복귀"였다는 점이 중요하다.**

### P2. 과병합의 직접 원인이 추론 설정에 있는데 건드려본 적 없음

`craft_text_detector` 패키지의 기본 디코딩은 **region score + affinity(link) score를 합쳐서**
connected component를 만든다. affinity는 원래 "인접 글자를 단어로 묶는" 신호라 이 설정
자체가 음절 병합을 유발한다. 파인튜닝 GT 설계 때는 이걸 정확히 이해해 affinity GT=0으로
만들었으면서(`IMPLEMENTATION_HISTORY.md` 10.2절), pretrained 추론 경로에서는 affinity가
그대로 살아 글자를 붙이고 있다. `link_threshold` 상향 / region 단독 디코딩은 비용이 거의
0인데 시도된 적이 없다.

### P3. Phase 4 자소→음절 병합 후처리가 "실패해서"가 아니라 "방향 전환으로" 폐기됨

Phase 4의 Union-Find 병합은 중대형 글씨에서 정확히 동작했다(test.jpg 12→10 정답, test6
18→12 정답). 문제는 소형 밀집 글씨의 파라미터 민감도였고, 그때 제안된 적응형 임계값은
**테스트도 안 해보고** 파인튜닝으로 넘어갔다. 파인튜닝이 실패한 지금, 이 폐기된 접근이
가장 유망한 카드로 되돌아왔다. 실제 앱 시나리오(연습장에 또박또박 쓴 글씨)는 Phase 4가
잘 되던 중대형 케이스에 가깝다.

### P4. 성능 요구사항(CRAFT 추론 500ms)이 한 번도 측정 안 됨

CPU에서 long_size=1280 CRAFT 추론은 통상 1~3초. 요구사항은 500ms인데 실측 데이터가 없다.
초과 시 long_size 축소 / ONNX 변환 / 요구사항 재협상이 필요한데 리스크가 숨어 있는 상태.

### P5. 캔버스 모드가 실제 사람 필기로 0번 검증됨

규칙 기반 구현 자체는 데이터 없는 상황의 최선이 맞으나, 모든 임계값(그룹핑 거리/시간,
`MATCH_QUALITY_THRESHOLD=0.6`, `SHAPE_WEIGHT=1.5`)이 합성 데이터로만 튜닝됐다. 팀원 필기
몇십 글자만 받아도 임계값이 통째로 어긋나는지 확인 가능한데 아직 안 했다. 획순 분석의
전제인 제시형 UI가 프론트에 없는 병목은 별개로 존재(`HANDOFF.md` 참고).

### P6. (경미) 서버 탑재 준비 부족

`ai/` 모듈들이 bare import + `sys.path` 조작으로 얽혀 있어 백엔드에서 패키지로 import하면
깨짐. `craft_detector.py`의 `detect()`에 `print()`가 박혀 있음. 인스턴스마다 모델을 새로
로드함(서버에서는 싱글턴 필요).

## 2. 단계별 계획

핵심 원칙: **파인튜닝 재시도는 최후순위. 그 전에 (1) 문제 크기를 실측하고 (2) 추론/후처리
쪽 싼 개선을 소진한다.**

| 단계 | 내용 | 성공 기준 |
|---|---|---|
| **1단계** | test_images + 실제 시나리오 사진에 음절 단위 정답 라벨링, 정확도(음절 일치율) 측정 스크립트 작성 | "박스 개수"가 아니라 GT 박스와의 매칭 기반 정밀도/재현율이 산출됨 |
| **2단계** | 추론 설정 실험: `link_threshold` 상향, region 단독 디코딩 | 1단계 지표로 과병합("한이" 붙음)이 감소하는 설정 확인 |
| **3단계** | Phase 4 Union-Find 병합 부활(git 히스토리에서 복원) + 적응형 임계값(med_w 기준 소형/중대형 분기) | 자소 과분할 케이스에서 음절 일치율 상승, 중대형 케이스 회귀 없음 |
| **4단계** | 전처리/추론/분석 소요시간 실측, 500ms 초과 시 long_size 트레이드오프 측정 | 단계별 지연시간 수치 확보, 필요 시 대응 방향 결정 |
| **5단계** | (팀 협조) 캔버스 파일럿 — 팀원 2~3명이 지정 글자 20~30자씩 실필기, 임계값 검증 | 실데이터에서 그룹핑/획순 판정이 육안 기대와 일치 |

**파인튜닝 재시도 조건**: 3단계까지 완료 후에도 음절 일치율이 목표(추후 1단계 결과 보고
설정) 미달일 때만. 그 경우에도 watershed pseudo-GT 정제 + 매 체크포인트
`debug_compare_production.py` 검증 필수.

- 발견한 함정: AI Hub GT는 원본 좌표계인데 전처리가 장축 1280px로 리사이즈함(3508→1280)
  → 스케일 보정 필수. 보정 전 F1이 전부 0.000으로 나왔던 원인.

**해석 — P1 진단이 정량으로 확정됨**
- 개수 비교가 문제를 심각하게 과소평가하고 있었다. AI Hub는 개수비 1.12~1.19로 "정답
  근처"처럼 보였지만 박스 정렬 F1@0.3은 0.08~0.16 — 지금 나오는 204개 박스는 172개
  음절과 거의 대응되지 않는 다른 모양의 영역들(자소 조각+단어 덩어리 혼재)이다.
- 폰트(test2)에서 과병합이 최악(25글자→8박스, 단어째 병합) — affinity가 붙이는 힘이
  깨끗한 텍스트일수록 강함. P2 가설(affinity 병합)과 일치.
- 큰 손글씨(test)는 F1@0.3 0.889로 양호 — 실제 앱 시나리오에 가까운 케이스가 가장 낫다.
- **개선 목표(2·3단계 판정 기준)**: 평균 F1@0.3 ≥ 0.7, 그리고 AI Hub 3장 각각 R@0.3 ≥ 0.5.
