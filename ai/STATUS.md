## 1. 이미지 모드 (사진 채점)

**✅ 이미 된 것** — 전처리(**측지 재구성으로 재작성, 2026-07-27**), 글자 탐지(CRAFT pretrained),
크기·기울기·자간·행간·기준선·획굵기 채점, 종합점수(교육 가중 3:2:1), 명료도 경고화, 절대 규범 축.

- **✅ 전처리 개편(2026-07-27, 상세: [DEVLOG.md](DEVLOG.md) 11막 / [IMAGE_PIPELINE_REBUILD_PLAN.md](IMAGE_PIPELINE_REBUILD_PLAN.md))** —
  adaptiveThreshold → **채널 max + 조명 정규화 + 측지 재구성**(비침·괘선 원천 제거). 확정 사항:
  - **리사이즈 = A방향(풀해상도 유지, 다운스케일 없음)**. 장축<800만 업스케일. ⚠️ 8막의 "리사이즈 유지(다운스케일)가
    정답"은 **뒤집혔다** — 그때 C(축소)가 나아 보였던 건 close 버그로 획이 깨진 상태였기 때문이고, close를
    고치니 A(풀해상도)와 탐지 동률이면서 원본 충실도가 높아 A 채택. glyph-aware(B)는 data/에서 열세라 미채택.
  - **close 버그 수정** — `CLOSE(fg)`(배경 close, 획 43% 소실) → `255-CLOSE(255-fg,2×2)`(잉크 전경 close).
  - **보존율 게이트 = coverage 방식**(percentile→coverage) — 연한 획 복구, 비침 이미지엔 recon 유지.
  - **탐지 크래시(T2) 수정** — `get_prediction(poly=False)`로 풀해상도 폴리곤 크래시 제거.
  - 단위 테스트 32개 통과. 유지 지표(크기·정렬·기울기)는 CV·각도라 **스케일 불변** — 리사이즈가 채점을 왜곡 안 함(실측).
- **⛔ 남은 개편 작업(T4·T5·T7, 미착수)** —
  - **T4 분석기 정리**: `analysis/handwriting_analyzer.py`에서 획 굵기·글자별 slant 제거, **문장 기울기**
    (행별 박스 중심선 회귀 기울기, deskew 이전 좌표) 추가. 아직 안 함 — 현재 분석기는 옛 6지표 그대로.
  - **T5 GT 재라벨**: 전처리 좌표계가 바뀌어 기존 7장 GT는 새 파이프라인엔 무효. 재라벨 필요(`/gt-labeling`).
  - **T7 검증**: T5 후 새 GT로 F1 재측정. **현재 새 파이프라인 F1은 미측정**(아래 F1 0.938은 옛 파이프라인 값).

- **🟡 탐지 정확도 한계** — 소형 밀집(모델이 반응 안 함, 후처리 불가·확정된 한계) / 흘림(test4·5·7
  라벨링 완료로 정량화됨: F1@0.3 0.87~0.93, 과병합 경향 ratio 0.82~0.98) / 좁게 붙인 2음절('오른'·'급한',
  기하만으론 분리 불가) / 획 굵기 과대측정(윤곽선 이진화 사진) / 기울기 게이트 보수적.
  근거: `archive/DETECTION_IMPROVEMENT_PLAN.md`.
- **🟡 평가셋·정답지(GT)** — 표본 **7장(537음절)**로 확장(2026-07-23): test4(239)·test5(39)·
  test7(62) 라벨링 완료 — **탐지기 미사용 독립 라벨**. 이제 **브라우저 라벨링 GUI**(`eval/label_gui.py`
  → 사람이 클릭으로 음절 묶기·분할 → `label_helper.py build`)로 만든다. AI가 이미지를 판독하지 않아
  토큰을 안 쓰고 흘림도 정확. 절차·관례는 `gt-labeling` skill. 흘림 포함으로 상방 편향 축소:
  평균 F1@0.3 **0.968(4장) → 0.938(7장)**, 흘림 개별 0.87~0.93 (F1@0.5 평균 0.894).
  GT 관례: 문장부호·긴 장식획 제외, 영문(TEST)은 글자별 1박스. 남은 것: **줄노트(괘선) 사진** 등 도메인
  추가(전처리에 괘선 제거 없음 — 미검증). 미라벨 후보는 이미 확보: `test_images/test8~10.jpg`,
  `test_line1~3.jpg`(줄노트).
- **🟡 후처리 과최적화 미측정 (홀드아웃 없음)** — 평가셋 7장이 **개발셋이자 테스트셋**이다. 탐지 개선
  1~14단계를 이 7장으로 F1 재며 채택했으므로 **7장에만 맞는 규칙일 위험**이 있고, 일반화 성능은 아직
  한 번도 측정되지 않았다.
  - *의심(임계값 튜닝 성격)*: 적응형 `long_size`, 과폭 박스 분할, region 피크 근접 2음절 분할. 단 적응형
    `long_size`는 일반화 장치일 수도 있어 **아직 가설** — 측정으로 판정할 것.
  - *안전(원리 기반)*: `link=1.0`(한글=음절), 자소→음절 병합(한글 구조) — 7장과 무관하게 성립.
  - *측정법*: GT 없이 가능. 라벨 안 된 새 사진에 **후처리 on/off 박스를 나란히 렌더링해 눈으로 비교**하면
    "규칙이 이상한 짓을 하는가"가 보인다. 문제없으면 과최적화 우려를 닫아도 된다.
  - *자산*: `test_images/test8~10.jpg`·`test_line1~3.jpg`(미라벨, 커밋 `d6faa53`에서 의도적으로 평가셋에
    넣지 않음) = 홀드아웃 후보. `test_line`은 위의 **괘선 미검증** 건도 같이 확인된다.
  - *분업*: 렌더 스크립트는 AI가 생성, 최종 판단(눈 비교)은 사람이. 저비용이라 통합(§3) 전에 먼저 하기 좋음.
- **✅ 순환성 편향 측정(2026-07-23, test3_crop)** — 기존 GT(탐지기 초안 기반) vs 독립 재라벨링 GT를
  비교: 두 GT 상호 평균 IoU **0.992**(140쌍, 129쌍은 IoU>0.99), 탐지 F1도 어느 GT로 재든 차이 ≤0.007
  (기존 0.821/0.908 vs 독립 0.828/0.908). → **순환성 편향 사실상 0.** 결론: **기존 4장 재작업 불필요,
  7장 통합 평균 유지 OK.** 4장(0.968)과 3장(0.87~0.93)의 격차는 순환성이 아니라 **난이도(흘림) 차이**이므로
  "쉬운 4 + 흘림 3" 구성만 명시하면 됨. 한계: 1장 표본(나머지 3장은 더 쉬워 편향 더 낮을 것으로 추정).
- **✅ 평가 지표 강화(2026-07-23)** — `evaluate_detection.py`에 **merge/split 분리 측정** 추가.
  F1·count_ratio가 상쇄로 숨기던 오류 구성이 보임(예: test3_crop ratio 0.95인데 분할 9·병합 14,
  test4 병합 43·분할 5). 후처리 개선 시 "병합↓/분할↑" 진단에 사용.
- **🤝 속도(레이턴시)** — 목표 500ms(REQ-004I-1)인데 CPU 실측 1.8~11초 → GPU/비동기/ONNX 없이는 불가.
  요구값 하향 개정 또는 인프라 결정 필요.
- **🟡 규범 임계값 임시값** — `TILT_NORM_DEG=7`·`LINE_NORM_MIN_RATIO=1.0`·`WORD_GAP_RATIO=0.55`·가중치
  3:2:1 모두 초안. 실데이터로 재튜닝. 근거: [NORM_STROKE_RESEARCH.md](NORM_STROKE_RESEARCH.md) §1·§3.
- **🟡 문서 낡음** — [handwriting_evaluation.md](handwriting_evaluation.md)가 갱신됨(구현 완료 반영).

## 3. 통합 · 범위

- **🤝 백엔드 통합(실서비스 실질 블로커)** — 어댑터 `backend/app/services/ai_adapters.py` 실구현은 있음.
  남은 것: ① 브랜치 병합(ai-setup 실구현 채택) ② 라우트가 AI 전처리/분석 쓰도록 결정(⚠️ 정확도는
  전부 AI 전처리 전제 — 다른 방식 섞으면 보장 안 됨) ③ bbox "전처리 후" 좌표계 오버레이 합의 ④
  backend `requirements.txt`에 torch 추가. 근거: [HANDOFF.md](HANDOFF.md) §5.1.
- **⚠️ 통합 시 터질 위험 2가지 (통합 전 반드시 합의)** — ②③이 왜 단순 협의가 아니라 위험인지:
  1. **전처리 체인 의존** — 탐지 성능은 특정 체인(**측지 재구성**+deskew+distance transform) 전제다.
     백엔드가 다른 전처리(예: 단순 이진화)를 쓰면 성능은 무보장. 이건 **파인튜닝 2차 실패
     (학습 65개 vs 실제 3개 탐지 — 도메인 불일치)와 정확히 같은 구조**다. 근거: [DEVLOG.md](DEVLOG.md) 3막.
     (리사이즈는 07-27부터 **A방향=다운스케일 없음**이라 "리사이즈 스킵" 위험은 사라짐 — 오히려 풀해상도 유지가 기본.)
  2. **좌표계** — 반환 bbox는 **"전처리 후" 좌표**(deskew 회전 반영, 큰 사진도 다운스케일 없어 배율≈1.0,
     장축<800 입력만 업스케일 배율)로 확정. 프론트가 **원본 사진 위에 그리면 deskew 회전만큼 어긋난다 =
     통합 첫날 터지는 종류**의 버그. 오버레이는 전처리 이미지 위에 그리는 것이 계약.
  - **AI 파트가 준비할 것**: ⓐ 어댑터(`preprocess_image` 드롭인)로 백엔드가 AI 전처리를 그대로 쓰게
    강제 — *구현은 이미 됨, 라우트 반영만 남음* ⓑ 좌표계 계약 명문화(반환 bbox=전처리 후 좌표,
    오버레이=전처리 이미지 위) ⓒ 오버레이용 전처리 이미지를 응답에 함께 반환.
  - 나머지(브랜치 병합·라우트 결정·torch 의존성)는 AI 혼자 못 정함 → 백엔드 트랙 협의.
- **⏸ 범위 밖(청사진)** — 개인화·실시간 영상(YOLO)·OCR 텍스트 변환·자유필기 획순 채점. 이번 범위 =
  두 모드 분석 + 학습 대시보드(SFR-008)까지. 근거: [requirement.md](requirement.md).

  생김 ② 정밀 수동 GT(197음절, 2차 검수) ③ 검증 전용 `debug_compare_production.py`. → 예전의 "시점 잘못
  고르기" 실수를 원천 차단 가능.
- **다시 한다면 — 바꿔볼 가설** — ① 정답지 정밀화(watershed로 pseudo-GT 정제) ② distance-transform이
  학습 땐 신호를 약화했을 가능성 → 빼고 비교 ③ 학습률/스케줄 과했을 가능성.
- **✋ 절대 규칙** — 매 체크포인트를 **실제 `CraftDetector`(기본 threshold)로 검증**(자체 loss 믿지 말 것).
  재도전 조건 = 다른 개선 다 해도 목표(평균 F1@0.3 ≥ 0.7, AI Hub 각 R@0.3 ≥ 0.5) 미달일 때만.
- **재사용 자산** — `craft_model.py`(구조 완전 호환), 학습 파이프라인 전체(OHEM·도메인 일치), `gt_generator.py`,
  `kaggle_finetune.py`(resume), `debug_compare_production.py`(검증), `craft_finetuned_epoch9.pth.bak`(보관).

## 5. 우선순위 제안

1. **[저비용·선행]** 후처리 과최적화 측정(§1) — test8~10·test_line으로 on/off 렌더 비교. AI 파트 혼자
   가능하고 하루면 끝난다. 결과가 "문제없음"이면 우려를 닫고 2번에 집중, 문제면 통합 전에 후처리부터 손봐야
   하므로 **순서상 앞**이다.

5. **[정리]** 규범 임계값은 실데이터 모이면 재튜닝
6. **[조건부·후순위]** 파인튜닝 재도전(§4) — 3번 갖춰지고 시간 여유 있을 때만
