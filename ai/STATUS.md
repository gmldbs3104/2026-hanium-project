## 1. 이미지 모드 (사진 채점)

**✅ 이미 된 것** — 전처리(**측지 재구성 + 연한글씨 보존 라우팅, 2026-07-27~31**), 글자 탐지(CRAFT pretrained,
**새 파이프라인 F1@0.3 0.891 검증**), 크기·기울기(문장 기울기)·자간·행간·기준선 **5지표** 채점, 종합점수(교육 가중
3:2:1), 명료도 경고화, 절대 규범 축.

- **✅ 전처리 개편(2026-07-27, 상세: [DEVLOG.md](DEVLOG.md) 11막 / [IMAGE_PIPELINE_REBUILD_PLAN.md](IMAGE_PIPELINE_REBUILD_PLAN.md))** —
  adaptiveThreshold → **채널 max + 조명 정규화 + 측지 재구성**(비침·괘선 원천 제거). 확정 사항:
  - **리사이즈 = A방향(풀해상도 유지, 다운스케일 없음)**. 장축<800만 업스케일. ⚠️ 8막의 "리사이즈 유지(다운스케일)가
    정답"은 **뒤집혔다** — 그때 C(축소)가 나아 보였던 건 close 버그로 획이 깨진 상태였기 때문이고, close를
    고치니 A(풀해상도)와 탐지 동률이면서 원본 충실도가 높아 A 채택. glyph-aware(B)는 data/에서 열세라 미채택.
  - **close 버그 수정** — `CLOSE(fg)`(배경 close, 획 43% 소실) → `255-CLOSE(255-fg,2×2)`(잉크 전경 close).
  - **보존율 게이트 = coverage 방식**(percentile→coverage) — 연한 획 복구, 비침 이미지엔 recon 유지.
  - **탐지 크래시(T2) 수정** — `get_prediction(poly=False)`로 풀해상도 폴리곤 크래시 제거.
  - 단위 테스트 32개 통과. 유지 지표(크기·정렬·기울기)는 CV·각도라 **스케일 불변** — 리사이즈가 채점을 왜곡 안 함(실측).
- **✅ 연한 글씨 손실 수정(2026-07-30, 커밋 1fc09cb)** — 측지 재구성이 seed 없는 연한 획을 비침처럼 지우던
  버그(test7·test5·data/). **이미지별 라우팅** 도입: near-black 진짜 잉크(진한 앵커)가 없으면 gentle(연한 글씨
  보존), 있으면 geodesic(비침 제거). 세기·sharpness로는 연한글씨≡비침 구분 불가라 이미지 단위로 갈랐다(DEVLOG 12막).
- **✅ T4 분석기 정리(커밋 b9d7ed5)** — 획 굵기·글자별 slant 제거, **문장 기울기**(행별 박스 중심선 회귀, 전처리
  좌표 — deskew 역회전 안 함, 사용자 결정) 도입. 채점 5지표(3:2:1).
- **✅ T5·T7 완료(커밋 386c71c)** — 새 파이프라인 기준 GT 재라벨 후 F1 측정. **F1@0.3 0.891 / @0.5 0.820**(12장).
  옛 0.938은 dev=test·다른 이미지셋이라 직접 비교 아님(동급). 오류는 과병합(merge) 우세.
- **⚠️ 미구현**: 비침이 gentle로 통과해 유령 박스가 나오면 **"깨끗한 종이 재촬영" 안내**(탐지/품질 단계) —
  사용자 방침(연한 글씨 손실보다 유령→재촬영이 낫다). 아직 안 만듦.
- **✅ 측정 불가 지표가 만점으로 나가던 문제 — 2026-08-12 해결(통합본에서 구현, DEVLOG 18막)**
  - AI가 `.get("score")`로 **`None`을 그대로** 내보낸다(폴백 100.0 제거, 글자 0개 조기반환 포함).
  - 백엔드가 **5지표를 전부 `metrics`에서 `_metric_score()`로** 읽는다 — 최상위 편의 필드 의존을 없애
    거짓말할 구조적 여지를 제거했다. 응답 스키마 3필드도 `Optional[int]`로 바꿨다.
  - 피드백 문구는 `_score_feedback()`이 **`None`이면 아무 문구도 만들지 않는다** — 안 잰 지표로
    칭찬도 지적도 하지 않는다.
  - 대시보드는 `or 0`을 없애고 **`None` 항목을 집계에서 뺀다**. 검증: 안 잰 "기울기 일관성"이
    26.7점(최하위 취약항목) → 80.0점(측정된 세션 기준).
  - ✅ **글자 0개 건도 함께 해결** — 탐지 0개면 `/analyze`가 **400**("사진에서 글자를 찾지 못했습니다")을
    준다. 종전엔 통과시켜 종합 100점·"우수"가 나갔다. 프론트는 `serverMessage`를 이미 띄우므로 수정 불필요.

## 2. 캔버스 모드 (태블릿 직접 쓰기)

- **⛔ 어떤 글자를 쓰는지가 서버에 전달되지 않는다(2026-08-06 발견) — 배관 문제, 인식 모델 불필요**
  실사용에서 **모든 글자가 "획이 1개 더 많습니다"**로 나오던 원인. 끊긴 곳은 둘이다:
  - ⓐ 프론트 `CanvasAnalyzeRequest`에 **글자 필드가 없다**(획 좌표·캔버스 크기·획 개수만).
    단 화면은 **제시형**이라 프론트는 정답을 알고 있다(`canvas_input_screen.dart:205`
    "점선을 따라 '$_currentChar' 글자를 연습해보세요").
  - ⓑ 백엔드 `handwriting.py:114`가 **`get_standard(db, char=None)`으로 하드코딩** — 프론트가 보내도 안 쓰인다.
  - → `DEFAULT_STANDARD` 반환 → 기대 획순 **빈 배열** → 획 개수 비교가 항상 "1개 초과".
    **크기 기준도 임의값 100×100**이라 크기 편차까지 무의미해진다(초기 `size_deviation: -100`의 정체).
  - **표준 데이터는 이미 있다** — 백엔드 `seed_stroke_standards.py`가 한글 분해로 **11,172자**를 시드한다
    (실제 적재 여부는 DB 확인 필요). **새로 만들 로직 없이 양쪽 한 줄씩.**
  - ⚠️ 아래 LSTM 스텁과 **별개 층위**다 — 글자를 알려줘도 스텁은 그대로 남는다.
- **⛔ AI의 캔버스 분석기가 통합본에 연결된 적이 없다(2026-08-06 발견) — 계약의 구멍**
  백엔드는 `analyze_canvas_writing`도 `analyze_stroke_order_by_position`도 **부르지 않는다.**
  3함수 계약이 캔버스 쪽은 **스텁 2개만** 노출하고, 백엔드는 그룹핑·크기·자간·점수를 **자체 구현**했다.
  → **실사용 경로의 획순 판정은 지금도 "획 개수 비교"가 전부.** 위치·순서 오류를 못 잡는다.
  - ⚠️ 종전 STATUS·HANDOFF·CLAUDE.md의 **"스텁 대신 `analyze_stroke_order_by_position`이 대신
    동작한다"는 `ai/` 패키지 안에서만 참**이었다(2026-08-06 정정). 통합본에서는 거짓.
  - 함께 버려지는 것: 필압·속도 프로필, 교정 플래그, 복수 정본 안내. 그리고 **자간·크기 기준이
    AI(상대)와 백엔드(절대)로 서로 다르다** — 같은 글씨에 다른 점수가 나온다. 목록: [DATA_FLOW.md](../DATA_FLOW.md) §8.

- **🤝 위 오버레이를 어떤 배경 위에 그릴지 — 팀 논의 대기(2026-08-05 대안 2안 정리)**
  세 안 모두 좌표는 정확해진다. 차이는 **사용자가 무엇을 보느냐**와 **비용**이다.

  | 안 | 배경 | 비용 | 비고 |
  |---|---|---|---|
  | **A. 이진 전처리 이미지** | 흑백 이진화 | **0** — `image.py:88`이 이미 보내는 중, 프론트만 수정 | AI가 실제로 본 것이 보인다 |
  | **B. 회전만 한 컬러** ⭐ | 자기 사진 | 작음 — AI 몇 줄 + 반환 키 1개 추가 | 자연스럽되 AI 시야는 가려짐 |
  | C. 박스를 역회전 | 자기 사진(원본) | 큼 — 각도 계약 추가 + 폴리곤 모델 | 축 정렬 사각형이 깨져 모델 변경 필요 |

  - **B가 왜 싼가**: Step 1~5(그레이·잉크 재구성·이진화)는 **크기를 안 바꾼다**. 좌표에 영향을 주는 건
    Step 6(회전)·Step 7(리사이즈)뿐이므로, 원본 컬러에 **같은 각도로 `_rotate_image` → 같은 최종 크기로 resize**만
    하면 좌표가 정확히 일치한다. **채점 경로(`binary_image`)는 그대로** — F1·점수 불변. 파이프라인 재구성 아님.
  - **B의 실질 비용은 용량뿐**(base64 실측): 이진 PNG 34~91KB vs 컬러 JPG 원크기 184KB~**1.2MB**(폰 사진).
    → **표시용이므로 장축 1280으로 축소해 보내면 130~170KB**. 종횡비만 유지하면 배율이 상쇄되어 **좌표는 그대로 맞다**
    (업스케일이 무해한 것과 같은 원리).
  - **B의 손봐야 할 곳**: `_rotate_image`가 이진 전용(`borderValue=0`·`INTER_NEAREST`)이라 컬러용은
    흰 여백·`INTER_LINEAR`로. 좌표엔 영향 없음. 그리고 `preprocess_image_full` 반환 dict 키 추가는
    기존 사용처를 깨지 않으므로 **`AI_MODEL_INTERFACE.md` 위반이 아니라 백엔드 합의 대상**이다.

   - 🤝 **먼저 정할 것: "비침 가능" 경고 문구만 띄울지, 실제로 유령 박스를 짚어내는 로직을 만들지.**
     후자는 신뢰도 값이 못 쓰게 돼 있어 새 방법을 찾아야 하므로 비용이 훨씬 크다. 팀 결정 후 착수.
3. **[프론트 결함 + 🤝 논의]** 오버레이가 원본 사진 위에 그린다(§3) — 괘선 종이에서만 반 글자 밀리고
   무지 종이 테스트로는 안 잡힌다. **배경을 A(이진, 비용 0)로 갈지 B(회전만 한 컬러, 자연스러움)로 갈지
   팀 결정 필요** — B는 AI가 몇 줄 추가(채점 경로 불변). 앱에 이미지 첨부가 생기면 즉시 검증.
4. **[팀]** 속도/GPU 결정(§1 🤝) — CPU 1.8~11초 vs 목표 500ms. 요구값 하향 개정이냐 인프라냐.
   **사용자가 팀과 직접 논의 중(2026-08-06).** ⚠️ 전처리 리사이즈를 되돌려도 안 빨라진다(§1).
4-1. **[팀·AI 밖]** 미구현 3건(§3) — **추천 연습 예문**(누가 만들지) · **이미지 S3 저장**(붙일지 뺄지) ·
   **계정 삭제**(엔드포인트·응답 스펙). 셋 다 결정만 나면 AI 몫은 없다.
5. **[캔버스·팀]** 실사용자 데이터 수집(§2) — LSTM 2곳 스텁 교체의 **선행 조건**. 데이터 없이는 못 함.
   **사용자 방침(2026-08-05): 앱 구현 완료 후 최종 제출 전까지 팀 내부에서 계속 사용하며 수집한다.**
6. **[조건부·고비용]** 파인튜닝 재도전(§4) — 과병합(하드 리밋) 개선의 유일 레버. F1 하니스+GT 갖춰짐, 단 3회 실패.
7. **[정리]** 규범 임계값은 실데이터 모이면 재튜닝. 평가셋 도메인 추가(폰 카메라)는 필요 시.
   ⚠️ 지금 정할 수 있는 건 **"어떤 항목을 노출할지"까지**고, 숫자(7°·가중치·문구 경계 60/85)는
   **캔버스 데이터 수집과 같은 시점**으로 밀린다(2026-08-06 정리).

> **이미지 모드 실측 평가는 앱 구현 이후로 미룬다(사용자 결정, 2026-08-05).** 현재 앱은 촬영만 지원해
> 이미지 첨부가 없고, 웹캠(1280×720·탐지 박스 9~12px·괘선 없음)은 실서비스 입력과 도메인이 달라
> 채점 타당성 판단 근거로 쓸 수 없다. 3번 검증도 이 시점에 함께 한다.
